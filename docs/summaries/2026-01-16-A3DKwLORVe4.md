# 建立多代理人系統的設計抉擇：子代理人架構

## 重點摘要
本影片介紹了在建構「子代理人」（Sub-Agent）或稱「主管」（Supervisor）架構時，需要做出的三大關鍵設計決策：同步與非同步的執行方式、工具設計（為每個代理人建立專屬工具，或使用單一分派工具），以及針對代理人規格、輸入與輸出的情境工程。這些選擇將直接影響系統的簡易性、反應速度和控制精度。

## 故事大綱
- 開場：影片首先回顧了子代理人架構，其中一個主代理人（Main Agent）接收使用者請求，並將任務分派給多個子代理人平行處理，最後由主代理人匯總並回覆最終結果。
- 中段：影片深入探討了三個核心設計領域。第一，**同步 vs. 非同步執行**，同步模式下主代理人會被阻斷並等待子代理人完成，模式簡單但延遲高；非同步模式下子代理人作為背景任務執行，反應快但架構複雜。第二，**工具設計**，開發者可以為每個子代理人建立一個專屬工具，以獲得精細的 I/O 控制權；或者使用一個能呼叫任何子代理人的「單一分派工具」，此法更具擴展性。第三，**情境工程**，亦即如何定義代理人的能力、客製化傳遞給它的輸入（如加入專業等級參數），以及如何處理它回傳的輸出（例如只回傳最終答案或完整對話歷史）。
- 結尾：影片總結道，子代理人架構對於平行任務和分散式團隊開發非常有效，但要成功建構一個高效的多代理人系統，仔細權衡上述的設計決策至關重要。

## 關鍵見解
1.  **同步與非同步是延遲的權衡**：當主代理人必須依賴子代理人的結果才能繼續時，應選擇簡單的同步模式。若任務獨立且使用者體驗對延遲敏感，則應選擇反應更快的非同步模式。
2.  **工具設計影響控制與擴展性**：為每個代理人建立專屬工具，能讓你對其輸入和輸出進行最精細的客製化。反之，單一分派工具更適合擁有大量或動態變化的代理人的系統。
3.  **情境是子代理人表現的關鍵**：主代理人需要清晰的代理人「規格」（名稱、描述、參數）才能做出正確的委派。客製化輸入（如新增「專業等級」參數）和輸出（回傳完整歷史而非單一答案）是提升任務表現的強力手段。
4.  **代理人探索機制很重要**：使用單一分派工具時，你必須明確地讓主代理人知道有哪些子代理人可用，可以透過系統提示詞、工具參數，或是一個專門列出可用代理人的工具來實現。
5.  **架構支援分散式開發**：此模型允許不同團隊獨立開發各自的子代理人，使其非常適合大型專案。

## 精彩時刻
- **清晰的比喻**：解釋同步與非同步時，「在同步模式下，你的主代理人會被『阻斷』（blocked）... 在非同步模式下，那些子代理人則作為『背景任務』（background tasks）執行。」
- **實用的程式碼範例**：展示如何為一個「深度研究」代理人工具增加 `expertise`（專業等級）參數，以動態調整傳遞給底層模型的提示，從而客製化其回應。
- **真實世界架構**：提到「單一分派工具」的模式已經被 quad code 和 deep agents 等真實世界的專案所採用。

# Design Decisions for Building Multi-Agent Systems with a Sub-Agent Architecture

## TL;DR
This video outlines three key design decisions when building a sub-agent (or supervisor) architecture: choosing between synchronous and asynchronous execution, designing tools (one per agent versus a single dispatch tool), and applying context engineering to define agent specifications, inputs, and outputs. These choices create a trade-off between simplicity, responsiveness, and control.

## Story Flow
- **Beginning:** The video starts by reviewing the sub-agent architecture, where a main agent delegates tasks to multiple sub-agents for parallel processing and is responsible for returning the final response. This architecture's strengths in parallelization and distributed development are highlighted.
- **Middle:** It delves into three critical design areas. First, **Sync vs. Async Execution**, where the synchronous approach is simpler but blocks the main agent, while the asynchronous approach is more responsive but also more complex. Second, **Tool Design**, comparing the fine-grained I/O control of a "tool-per-agent" model with the scalability of a "single dispatch tool." Third, **Context Engineering**, which covers how to define an agent's capabilities, customize its inputs (e.g., by adding an `expertise` parameter), and process its outputs (e.g., returning only the final answer versus the full message history).
- **End:** The video concludes that while the sub-agent architecture is powerful for parallel tasks and team-based development, carefully considering these design decisions is critical to building an effective multi-agent system.

## Key Insights
1.  **Sync vs. Async is a Latency Trade-off**: Choose the simpler synchronous model when the main agent must have the sub-agent's results to proceed. Opt for the more responsive asynchronous model for independent tasks where user experience is sensitive to latency.
2.  **Tool Design Balances Control & Scalability**: A tool-per-agent approach gives you precise, custom control over the input and output for each agent. A single dispatch tool is better suited for systems with a large or dynamic number of agents.
3.  **Context is Key for Sub-Agent Performance**: The main agent relies on clear agent "specifications" (name, description, arguments) to delegate tasks correctly. Customizing inputs and outputs is a powerful way to improve task performance.
4.  **Agent Discovery is Crucial**: When using a single dispatch tool, you must explicitly inform the main agent about available sub-agents. This can be done via the system prompt, tool arguments, or a progressive disclosure method like a `list_agents` tool.
5.  **The Architecture Supports Distributed Development**: This model allows different teams to develop sub-agents independently, making it well-suited for larger projects.

## Notable Moments
- **A Clear Distinction**: When explaining sync vs. async: "In a synchronous way, your main agent is blocked... In an asynchronous way, those sub-agents run as background tasks."
- **A Practical Code Example**: Showing how to add an `expertise` parameter to a "deep research" agent tool to dynamically alter the prompt sent to the underlying model, thereby customizing its response.
- **Real-World Architectures**: The mention that the "single dispatch tool" pattern is used by real-world systems like "quad code" and "deep agents."
